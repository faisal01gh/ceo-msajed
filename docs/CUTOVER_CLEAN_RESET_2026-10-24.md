## قواعد التنفيذ

- قبل الحذف: جرد counts وexport محلي خاص لبيانات النظام الجديد الحالية لأغراض الرجوع فقط؛ لا يرفع إلى GitHub.
- حذف المعاملات يتم في معاملة DB واحدة أو migration موثقة تحفظ ترتيب FK/Cascade وتتحقق بعد التنفيذ.
- لا تعديل مباشر غير مدعوم على `auth.users`; إنشاء/حذف/تحديث Auth يتم عبر Supabase Auth Admin/المسار الإداري المعتمد.
- حذف QA يشمل Auth + profile + roles + permissions + aliases/registry المرتبطة، مع إثبات عدم بقاء orphan rows.
- تجهيز الموظفين يعتمد على أسماء/أدوار/إدارات السجل الموجود حاليًا ومصدر الموظفين وقرارات الهيكل؛ لا اختراع دور أو إدارة.
- الحسابات التي لديها Auth حقيقي يمكن الاحتفاظ بـUID الخاص بها، مع إعادة تهيئة كلمة مؤقتة فقط إذا لزم، باستثناء فيصل.
- الحسابات التي لا Auth لها تُنشأ وتربط بنفس canonical registry row.
- كل كلمة مؤقتة: عشوائية وفريدة، 16+ حرفًا، وتحقق سياسة القوة؛ لا إعادة استخدام.
- `must_change_password=true` للحسابات ذات الكلمة المؤقتة في كل مواضع الحالة اللازمة لمسار الدخول.
- بعد كل provisioning: تحقق إداري من الربط والحالة دون كشف كلمة المرور في السجل.
- بعد التنفيذ: Security Advisor وPerformance Advisor وSmoke للواجهة والدخول دون كتابة Business.
- التوثيق النهائي يسجل counts فقط ولا يسجل كلمات المرور.
