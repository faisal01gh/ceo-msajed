# خطة التطوير التقنية — GitHub + Supabase

آخر تحديث: 2026-10-03

## الهدف

تحويل `ceo-msajed` مباشرة إلى **التطبيق الجديد الفعلي** بدل مرحلة Figma.

النسخة الجديدة ستستخدم:
- GitHub للكود والنشر والتوثيق.
- `msajed-tasks` كمصدر بيانات حقيقية **للقراءة فقط في البداية**.
- `msajed-ceo-erp` كبيئة التطوير الجديدة لتسجيل الدخول الموحد والجداول الجديدة والكتابة التجريبية.

بهذا نرى البيانات الفعلية مبكرًا، بدون المخاطرة ببيانات النظام السابق.

## 1. GitHub هو مصدر الحقيقة

يحتوي المستودع على:
- المواصفات المعتمدة.
- سجل القرارات.
- الواجهة الأمامية.
- مخطط قاعدة البيانات.
- migrations.
- seed data تجريبية.
- الاختبارات.
- النماذج/prototypes.
- سجل التغييرات.

كل قرار معتمد أو تعديل على قرار سابق يحدث في المستودع أولًا بأول.

## 2. استراتيجية Supabase المعتمدة

### المشروع القديم: msajed-tasks
- Project ref: `urgkbbconlxeagfgyjee`
- يحتوي البيانات الحقيقية للنظام السابق.
- يستخدم في البداية كمصدر قراءة/توافق.
- لا نسمح للواجهة الجديدة بالكتابة عليه حتى اعتماد الوحدة ومسار الترحيل.
- يحتوي حاليًا أكثر من نموذج هوية: Supabase Auth + ceo_users + portal_users، لذلك لا نعتمد هذا الانقسام كنموذج الدخول النهائي.

### مشروع التطوير الجديد: msajed-ceo-erp

- الاختبارات والكتابة التجريبية.

### مبدأ الانتقال
نعرض البيانات القديمة عبر طبقة توافق، وننقل كل وحدة إلى الجداول الجديدة بعد اعتماد مواصفتها، بدل إعادة كتابة كل النظام دفعة واحدة.

## 3. البيئات

### Development
للتجربة اليومية والتعديلات السريعة.

### Staging
نسخة مستقرة للاختبارات النهائية وقبول المستخدم قبل الإنتاج.

### Production
لا يتم إنشاؤها/تعديلها ضمن هذا المسار إلا بعد اعتماد صريح من فيصل.

في المرحلة الحالية يمكن البدء بمشروع Supabase Development واحد، ثم فصل Staging عندما تبدأ المزايا بالاستقرار.

## 4. طريقة العمل

لكل وحدة:
1. تثبيت المواصفة في GitHub.
2. بناء الواجهة الحقيقية.
3. توصيلها ببيانات النظام السابق للقراءة.
4. اختبار الصلاحيات والظهور ببيانات فعلية.
5. إنشاء schema جديد للوحدة في `msajed-ceo-erp`.
6. تطبيق Auth/RLS.
7. تشغيل الوحدة الجديدة بالكتابة في بيئة التطوير.
8. مقارنة النتائج مع النظام السابق.
9. اعتماد فيصل.
10. بعدها فقط نحدد انتقال بيانات/كتابة الوحدة للإنتاج.

## 5. قاعدة البيانات

لا نعيد نموذج `app_state` القديم كسجل JSON ضخم.

نستخدم جداول مترابطة مستقلة مثل:
- users / profiles
- roles / role_assignments
- organizational_units
- user_memberships
- transactions
- transaction_assignments
- transaction_actions
- transaction_routes
- transaction_participants
- transaction_links
- transaction_history
- notifications
- delegations

ويتم تثبيت المخطط التفصيلي لكل قسم بعد إقفال مواصفته.

## 6. الصلاحيات والأمان

- لا تعتمد الصلاحيات على إخفاء الأزرار فقط.
- تطبق الصلاحيات في قاعدة البيانات عبر RLS/سياسات مناسبة.
- أي جدول exposed يجب أن يكون مؤمنًا.
- مفاتيح الخدمة والأسرار لا توضع في الواجهة.
- صلاحيات الدور + صلاحيات المستخدم + حالة المعاملة كلها تدخل في قرار السماح.
- تسجل العمليات المؤثرة في audit log.

## 7. الترحيلات

كل تغيير schema يعتمد يجب أن يكون migration محفوظًا في GitHub.

الهدف أن يستطيع أي مطور أو بيئة جديدة إعادة إنشاء قاعدة التطوير من:
- migrations
- seed data
- الإعدادات المحفوظة في المستودع

## 8. بيانات التجربة

نستخدم بيانات تجريبية فقط في Development/Staging.

بيانات الموظفين الفعلية الموجودة في المستودع تستخدم كمرجع للهيكل، ولا يتم إدخال بيانات حساسة أو أسرار في الواجهة أو ملفات عامة.

## 9. الانتقال للنظام الكامل

بعد إقفال الوحدات الأساسية واختبارها:
- المعاملات
- المهام
- التقارير
- التذكيرات
- المستخدمون والصلاحيات
- الاجتماعات/المتابعة
- الأرشيف والتدقيق

ننفذ مراجعة نهائية للمخطط والأمان والأداء، ثم نحدد خطة الانتقال للإنتاج.

## 10. قاعدة مهمة

GitHub + Supabase Development ليسا نسخة مؤقتة نرميها لاحقًا؛ بل هما **أساس النظام الكامل**.

ما نثبته بشكل صحيح في migrations والكود والصلاحيات ينتقل معنا لاحقًا إلى Staging ثم Production بدل إعادة البناء من الصفر.


## 11. ترحيل الحسابات النشطة

القرار المعتمد:
- لا ننقل حسابات الاختبار أو الحسابات غير التشغيلية.
- نعتمد سجلًا موحدًا للأشخاص التشغيليين في `account_migration_users` مع aliases للحسابات القديمة.
- لكل شخص حساب واحد نهائي في Supabase Auth داخل `msajed-ceo-erp`.
- أول دخول للنظام الجديد يستخدم بيانات الدخول القديمة **فقط للتحقق من هوية صاحب الحساب**.
- بعد نجاح التحقق يفرض النظام على المستخدم تعيين كلمة مرور جديدة للنظام الجديد قبل فتح النظام.
- لا تنقل كلمة المرور القديمة ولا hash الخاص بها إلى النظام الجديد.
- بعد اعتماد كلمة المرور الجديدة لا يعود النظام الجديد إلى كلمة مرور النظام القديم.
- النظام القديم وكلمات مروره تبقى كما هي دون تغيير.

الحسابات التشغيلية المعتمدة حاليًا: 12 شخصًا.
تم ربط 11 منهم مسبقًا بحسابات Auth في المشروع الجديد، والحساب المتبقي يُنشأ عند أول دخول فعلي له.

## 12. مسار القراءة السريع

تم فصل القراءة المتكررة للقوائم عن Edge Functions قدر الإمكان:

- قائمة المعاملات تستخدم RPC مباشرًا عبر PostgREST للمستخدم المسجل:
  `list_my_transactions`.
- دليل المستخدمين والإدارات الخاص بالمعاملات يستخدم:
  `transaction_directory_my`.
- الهوية والصلاحيات تستخرج من `auth.uid()` وسياق الحساب الجديد.
- عمليات القراءة تطبق الصلاحيات في قاعدة البيانات، ولا يرسل العميل هوية دور يثق بها السيرفر.
- عمليات الكتابة الحساسة تستمر عبر طبقة خلفية آمنة مع Audit.
- تحميل دليل المعاملات والقائمة يبدأ بالتوازي عند فتح الصفحة.

### نتيجة فحص الأداء

تم قياس استعلام قائمة المعاملات داخل PostgreSQL بحوالي **41 ms** في اختبار `EXPLAIN ANALYZE`.

السجلات السابقة قبل التحسين أظهرت طلبات Edge من السعودية استغرقت تقريبًا **1.5–2.4 ثانية**، لذلك كان الاختناق في طبقة Edge والتحقق المتكرر من النظام القديم، وليس في استعلام PostgreSQL نفسه.

لهذا تم:
1. نقل القائمة والفلاتر والـPagination إلى PostgreSQL.
2. إزالة تحميل كل المعاملات إلى JavaScript لغرض الفلترة.
3. قراءة القوائم مباشرة عبر PostgREST بعد اكتمال ترحيل الحساب.
4. تقليل جولات التحقق من الهوية.
5. تحميل الطلبات الأولية بالتوازي.

### Cloudflare

Cloudflare Pages يمكن استخدامه لاحقًا للواجهة والنطاق المخصص، لكنه **ليس العلاج الأساسي لبطء البيانات**؛ لأن استجابات Supabase Edge نفسها تمر أصلًا عبر Cloudflare، بينما الاختناق المقاس كان في مسار الـAPI والتحقق من الهوية.

لذلك لا يتم نقل الاستضافة إلى Cloudflare لمجرد معالجة البطء قبل قياس نتيجة التحسينات الخلفية الحالية.
