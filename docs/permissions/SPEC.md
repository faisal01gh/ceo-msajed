# مواصفة قسم الصلاحيات

آخر تحديث: 2026-10-04

## الهدف

إنشاء قسم مركزي باسم **الصلاحيات** لإدارة صلاحيات المستخدمين في النظام.

القسم قابل للتوسع حسب أقسام النظام التي ستضاف مستقبلًا.

## الوصول الإداري

إدارة الصلاحيات حاليًا لمدير مكتب الرئيس التنفيذي.

الحماية ليست واجهة فقط:
- القراءة والتعديل محميان في قاعدة البيانات.
- أي تعديل صلاحية يسجل في Audit.
- لا يستطيع المستخدم تجاوز القسم باستدعاء API مباشر.

## هيكل القسم

داخل قسم «الصلاحيات» توجد تبويبات حسب وحدات النظام.

### التبويب الأول المعتمد
**المعاملات**

### تبويبات مستقبلية
تضاف عند اعتماد وتنفيذ أقسام جديدة، مثل:
- المهام.
- المتابعة اليومية.
- التقارير.
- أي قسم آخر يعتمد لاحقًا.

لا تنشأ صلاحيات مستقبلية قبل اعتماد مواصفة القسم نفسه.

## نموذج الصلاحية

قرار السماح يعتمد على:
**الدور + صلاحيات المستخدم + نطاقه الإداري + حالة السجل/المعاملة.**

يوجد مستويان:
1. صلاحيات افتراضية موروثة من الدور.
2. Override للمستخدم:
   - سماح.
   - منع.
   - أو العودة للوضع الافتراضي للدور.

## تبويب «المعاملات»

يعرض المستخدمين التشغيليين وأدوارهم وصلاحيات المعاملات.

**قاعدة العرض المعتمدة:**
- جميع صلاحيات المعاملات المسجلة في النظام تظهر في هذا التبويب لكل مستخدم، حتى لو كانت الصلاحية موروثة أو مقيدة حاليًا بدور معين.
- لا تخفى الصلاحية لمجرد أن القرار الحالي يجعلها ثابتة لدور أو مستوى وظيفي.
- ظهور الصلاحية لا يعني وحده السماح بتنفيذها؛ الحماية الفعلية تبقى خاضعة للدور + صلاحيات المستخدم + نطاقه الإداري + حالة المعاملة.
- إذا تغير قرار إداري مستقبلًا بشأن دور أو مسمى أو تكليف، تعدل المواصفة والحماية الخلفية نفسها ثم تصبح الصلاحية قابلة للإدارة حسب القرار الجديد، دون إعادة تصميم قسم الصلاحيات.

الصلاحيات الحالية:
- إنشاء معاملة.
- إحالة وإسناد.
- تغيير الأولوية.
- تغيير مسؤول المعاملة.
- إغلاق معاملة.
- استرجاع معاملة.
- تحديد تاريخ الاستحقاق.
- إطلاع الرئيس التنفيذي.

صلاحيات مقيدة حاليًا وفق مواصفة المعاملات، **لكنها تظهر في التبويب ولا تخفى**:
- عرض جميع المعاملات.
- التصرف على جميع المعاملات.
- الحذف النهائي.

حالتها الحالية:
- «عرض/التصرف على الجميع» مرتبطان بنموذج مستوى الرئيس المعتمد.
- «الحذف النهائي» محصور بمدير مكتب الرئيس التنفيذي حسب مواصفة المعاملات.
- تظل ظاهرة في مصفوفة الصلاحيات حتى وهي غير قابلة للتعديل حاليًا.
- لا تعتبر هذه القيود أبدية؛ إذا اعتمد فيصل تغييرًا لاحقًا، يتم تحديث المواصفة والحماية الخلفية وفتح التعديل وفق القرار الجديد.

## سكرتير المساعد

الدور المعتمد:
`assistant_secretary`

الاسم:
**سكرتير المساعد**

لا توجد له صلاحيات معاملات موروثة من دور المساعد.

يستطيع أن يحصل على صلاحيات محددة فقط إذا منحت له صراحة من قسم الصلاحيات.

فهد وليد الرشيد:
- دوره: سكرتير المساعد.
- يتبع هايف نايف مطلق الدويش تنظيميًا.
- لا يعد مساعدًا.
- لا يملك «إطلاع الرئيس» أو أي صلاحية مساعد لمجرد المسمى.

## سجل التغيير

كل تعديل من قسم الصلاحيات يسجل في `audit_log` مع:
- من نفذ التعديل.
- المستخدم المستهدف.
- رمز الصلاحية.
- الحالة الجديدة.
- هل كانت الصلاحية موروثة من الدور أم Override.
- التاريخ والوقت.

## التوسع المستقبلي

عند إضافة قسم جديد:
1. تعتمد مواصفته.
2. تضاف صلاحياته برمز مستقل مثل `tasks.*`.
3. يظهر تبويب جديد داخل «الصلاحيات».
4. لا نغير نموذج قسم الصلاحيات أو ننشئ نظامًا منفصلًا لكل قسم.
